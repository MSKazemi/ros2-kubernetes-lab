See the idea in a minute

A robot has a sensor and a model to run. The model could run on a nearby edge box or in a faraway cloud. Press play or pick a step to see how a time budget decides. The picture is a sketch, and no timing has been measured.

Plain-language guide

Edge and cloud
The edge box is a computer close to the robot. The cloud is a faraway service, here a Kubernetes cluster or a hosted model service, reached over a network that can slow down or drop.
Latency budget
The longest time a result may take to come back and still be useful. A placement that goes past the budget is over budget.
Hard gate
An ordinary code check that removes placements that cannot work, such as ones that are unreachable, too slow or not allowed, before any ranking happens.
Jev
A structured decision model this research proposes to try as an optional adviser. It would only rank placements that already pass the gate. Its answers are advice, not commands.
01 / What are we studying?

One real research question, not a product claim.

A fictional camera-equipped robot needs to run a task-compatible perception policy. Local CPU and remote hosted inference have different cost and network risks. A deterministic gate removes impossible or stale placements before any model comparison.

Research hypothesis

Question: Does Jev's preference among already eligible placements improve simulated task outcomes over deterministic heuristics once action freshness and network overhead are measured?

Null hypothesis: Under the same hard constraints and fixed workload, Jev advisory selection yields no net outcome gain after hosted latency, outage and cost.

Alternative: A bounded soft preference helps choose among equally eligible locations in a reproducible simulation; no hard real-time claim.

Audience & learning targets

Edge AI · systems researchers · Kubernetes · MSc → PhD · Start with synthetic inputs

  • Separate compute placement policy from hard real-time robot control.
  • Apply numeric deadlines, data residency and memory bounds in code.
  • Design repeatable RTT, jitter, loss, disconnect and recovery profiles.
  • Collect action age, availability and cost without invented benchmarks.

Experimental protocol

  1. Fix the request stream, the deadlines and the network profile in a config file before running anything. Every parameter there is declared, not measured.
  2. Run all policies on the same seeded request stream, so differences come from the policy.
  3. Compare always_local, always_remote, deadline_aware and hedged_fallback on deadline misses and on the cause of each miss.
  4. Treat every number the simulator prints as SIMULATED. Real-network or real-robot evidence needs a separate, reviewed run.

The simulator never actuates anything: its sink only records would_apply or rejected. There are two sites only, the robot and one remote service, and no hold action: a request with no accepted answer is a deadline miss. Do not assume the remote wins. Under the simulator's placeholder parameters, running locally is not worse than always going remote, and other parameters could change that ordering. The registry primary metric (sensor-to-valid-action p95) has no measured value. See also the experiment blueprint on this page.

03 / Experiment blueprint

Variables, baselines and measurements.

Before anyone reports performance, the task, failure cases, comparison methods and test split must be fixed. Keep negative results and rejected advice visible.

Research dimensionProposed measurement contract
PlacementsLocal process, same-LAN remote policy, and Kubernetes remote policy after verified DDS/network prerequisites.
BaselineDeterministic hard constraints and latency/cost-aware heuristic; explicitly define an oracle for retrospective regret.
VariablesRTT, jitter, packet loss, disconnection duration, model service queue and approved data locality.
Failure casesLossy link, stale action chunk, provider timeout, remote policy unavailable, infeasible accelerator memory.
Primary metricsp50/p95/p99 sensor-to-valid-action age, missed deadlines, reject counts, availability and eligible-placement regret.
ReproducibilitySource SHA, simulator/model version, hardware/clock, network profile seed, placement eligibility snapshot and failures.

Suggested experiment procedure

  1. Describe a specific compatible simulator, model and task; otherwise remain on synthetic decision examples.
  2. Implement deterministic eligibility and establish a no-JeV local baseline with unit tests.
  3. Validate network fault injection and timestamp assumptions before collecting measurements.
  4. Compare placement advisories under matched workloads and fixed budgets, including outages.
  5. Publish raw timing/event records and explain what cannot be generalized to physical robotics.

What a contribution should produce

  • Synthetic placement matrices with eligible/ineligible candidates
  • Latency/network impairment run protocol
  • Immutable inference request and eligibility logs
  • p95/action-age/failure plots with raw runs (future)

Required before publishing a result: independent run ID, method, seed, source/model revisions, environment, raw measurements, executable analysis, errors/limitations and human review.
