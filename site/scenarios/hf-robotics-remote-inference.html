01 / Research challenge

Why this problem is interesting

A fictional simulated robot receives action chunks from an optional remote LeRobot server backed by an immutable HF checkpoint. ROS 2 DDS remains an independent middleware concern. Jev might advise only among prevalidated eligible locations and must never authorize/execute action chunks.

Falsifiable question

Does remote inference deliver fresh, valid actions under realistic network faults?

Working hypothesis

Remote GPU service may improve throughput for some compatible workloads but also raises action-age, availability and recovery risks under network impairment.

Null hypothesis

Remote inference does not improve the simulator's valid-action throughput or task outcomes compared with a compatible local baseline after accounting for network and failure costs.

Hugging Face capabilities involved

  • HF Hub model cache + pinned processor
  • Upstream LeRobot remote policy server
  • Zenoh transport (not ROS 2 DDS)
  • Kubernetes workloads after security review
  • Jev advisory eligibility review

Who can contribute?

Kubernetes and GPU services · Robot policy inference · Distributed systems research

Required prerequisites: Existing #14/#15/#16 modern DDS verification for cross-worker claims, #55/#59 safety contract, #58 revision/cache, #60 run manifest, #61 remote server, #62 edge study.

03 / Reproducible experiment design

Experimental variables, controls and metrics

A useful research scenario is more than a diagram. These are the testable claims and artifacts future contributors should implement or report.

Design elementHow it should be investigated
TopologySimulator client + same-host policy, LAN policy service, optional isolated Kubernetes GPU service; no real robot.
PrerequisitesModel/action contract, supported position-hold driver, authenticated Zenoh router when crossing boundaries, exact server/client revision.
ImpairmentsDelay, jitter, packet loss, disconnect, stale action, restart, wrong model revision and rejected unsupported driver.
BaselinesLocal synchronous; supported RTC mode only if appropriate; upstream remote LeRobot; optional Jev preference among eligible placements.
Endpointsp50/p95/p99 valid action age, deadline misses, simulator task completion, session failure/availability, GPU cost.
Fail-closed behaviorTimeout/stale chunk never becomes actuation authorization; no autonomous cluster mutation, raw /cmd_vel, or cross-worker DDS claims.

Proposed experimental steps

  1. Establish a working, compatible simulator rollout as local reference with complete model/processor identity.
  2. Read upstream LeRobot remote inference contract, distinguish Zenoh session from ROS 2 DDS and verify security mode.
  3. Prototype admission and timeouts with a CPU/mock provider offline before any GPU/Kubernetes resources.
  4. Only on approved hardware, run matched impairment profiles, log monotonic action age and all failed attempts.
  5. Study optional Jev placement advice separately, against deterministic eligibility and simulator-safe fallbacks.

Expected contributions

  • Reference remote inference architecture and contract matrix
  • Offline session rejection and stale-action test cases
  • Versioned optional Kubernetes deployment checklist and network research protocol
  • Measured action-age/recovery results only after real simulator runs

Publication gate: no result without a source revision, licensed data, raw positive and negative runs, exact method, uncertainty, and human review.

Safety and deployment limitations

Do not ship private video, motor command streams, sensitive lab addresses, access tokens or unlicensed model weights. Hard eligibility, quotas, version checks, deadlines and actions remain in deterministic code. Jev is advisory only where included.

Hugging Face integration and external model services may require credentials, licensing review, a subscription or usage charges. Public demos must not claim any official partnership or endorsement.
