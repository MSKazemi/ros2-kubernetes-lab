SCENARIO 04 · P2 / SIMULATOR RESEARCH

Fair Multi-Robot Task Assignment with Jev Advisory Ranking

Three simulated robots have different capabilities, reservations and energy budgets. Who should get the next task—and how can we measure fairness?

See the idea in a minute

Three simulated robots can each do a different job, and a dispatcher picks who gets the next task. Compare two ways of choosing, one step at a time. The tasks are made up and no result has been measured.

Plain-language guide

  • Dispatcher: the scheduler code that picks which waiting task goes to which robot.
  • Eligible robot: a robot that has the needed capability, is not reserved elsewhere and has enough energy. The scheduler removes all others first.
  • Fairness: whether every robot and task type gets served, instead of one waiting far longer than the rest. The plan is to compute Jain's fairness index in code.
  • Jev ranking: optional qualitative advice that ranks only eligible robots. The deterministic scheduler keeps the final say.
01 / What are we studying?

One real research question, not a product claim.

In a fictional lab, a scout robot can inspect markers, a carrier delivers mock parcels and an arm manipulates objects in simulation. A scheduler must first remove unavailable or incapable robots before asking which candidate best fits.

Research hypothesis

Question: Does Jev's qualitative ranking among eligible simulated robots improve task fit and completion compared with constrained round-robin or cost-aware deterministic schedulers?

Null hypothesis: Jev's rank offers no reproducible improvement after controlling for task feasibility, arrival order, reservations and resource overhead.

Alternative: Jev helps choose semantic fit in ambiguous cases while a deterministic scheduler alone enforces feasibility, fairness and capacity.

Audience & learning targets

Multi-agent systems · OR · robotics researchers · MSc → PhD · CPU-only fixtures first

  • Model robotic capabilities and authorization as hard constraints.
  • Compare round-robin, greedy and cost-aware scheduling baselines.
  • Use seeded task arrivals and congestion to measure fairness.
  • Record invalid suggestions and no-eligible-robot outcomes.

Deficit round robin gives each backlogged robot a turn, so the burst cannot hold the worker for long.

  2. Every request is admitted passed

    No queue_capacity is set.

  3. DRR serves each backlogged robot in turn info

    Each turn adds the quantum, 0.1 s, to a robot's deficit. A request costs its service time, 0.1 s, so each turn serves one request.

    ring: noisy-f, robot-a

  4. Robot-a is served after one burst request passed

    At 0.1 s noisy-f takes one turn. At 0.2 s it is robot-a's turn, so robot-a runs 0.2 s to 0.3 s and meets its deadline.

    robot-a: finish 0.3 s

  5. Fairness and miss-rate: N/A N/A (not run)

    Jain fairness is computed over each robot's on-time ratio. When DRR delays the noisy robot, the index can go down even though the quiet robot now meets its deadline, so a higher index is not simply fairer. Read it next to the quiet-robot miss rate. Both would be SIMULATED values from a full run, and none are shown.

Outcome: accepted DRR bounded the quiet robot's wait without looking at deadlines. Its cost, such as longer delays and tail latency for the noisy robot, is exactly what a full run would have to measure.

Experimental protocol

  1. Write the scenario as a config: robots as clients, their arrival patterns, deadlines and the models they use. Every number is an assumption, not a measurement.
  2. Run fifo, edf and drr on the same seeds, with first_idle and cache_aware worker placement. Use the default fleet for queue disciplines and the cache-pressure scenario for placement.
  3. Read deadline-miss rate, nearest-rank latency percentiles, starved requests, cache hit rate and Jain fairness together, never one alone.
  4. Inject a worker-down window to test recovery, and report only what a recorded run produced.

Everything the simulator prints is labelled SIMULATED, from assumed parameters. Jain fairness is computed over per-robot on-time ratios, so it can fall when a fair scheduler pushes the noisy robot late. Read it together with the quiet-robot miss rate and the goodput rate. Worker placement (first_idle or cache_aware) only matters when models compete for cache space, which is what the cache-pressure scenario is for. See also the experiment blueprint on this page.

03 / Experiment blueprint

Variables, baselines and measurements.

Before anyone reports performance, the task, failure cases, comparison methods and test split must be fixed. Keep negative results and rejected advice visible.

Research dimensionProposed measurement contract
FleetFictional scout (camera), arm (grasp) and carrier (parcel) with fixed capability and reserve states.
BaselineConstrained round-robin, greedy shortest estimated task time, capacity/fairness heuristic.
VariablesTask arrival mix, reservations, simulated low battery, robot outage, queue size and uncertain task semantics.
Failure casesIneligible capability, insufficient reserve, conflicting exclusive tasks, spoofed state, no available robot.
Primary metricsSimulator task completion, queue wait, invalid suggestion rate, utilization, Jain's fairness index computed in code.
ReproducibilitySeeded workload generator, queue and capability matrices, fixed schedule budget, full task-allocation trace.

Suggested experiment procedure

  1. Define a tiny synthetic, licensed fleet/task schema with hard capabilities and budget constraints.
  2. Implement deterministic eligible-set filtering plus a no-JeV allocation baseline.
  3. Prepare fixed task-arrival seeds, failure injection and fair-scheduling comparison definitions.
  4. Optionally use Jev Choice only among eligible robot IDs and record advice vs actual assignment.
  5. Execute a verified simulator study before reporting completion or fairness results; preserve negative runs.

What a contribution should produce

  • Synthetic robot capability and task-arrival fixture definitions
  • Constraint-aware baseline scheduler tests
  • Simulator trace/run manifest with seeds (later)
  • Plots of fairness, waiting time and task success after verified runs

Required before publishing a result: independent run ID, method, seed, source/model revisions, environment, raw measurements, executable analysis, errors/limitations and human review.
